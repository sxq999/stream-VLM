# MiniCPM-o + vLLM-Omni：执行计划

使用 `openbmb/MiniCPM-o-4_5` 官方权重，复用 vLLM-Omni 双工执行。当前进度以[结果](results.md)为准，固定版本见[来源](sources.md)。本文件中未完成的交付均为待办，不代表现有脚本已经提供完整能力。

## 边界与分工

```text
实验程序：准备媒体、按时提交、记录与分析
                    ↓
官方 vLLM-Omni：长期会话、Thinker → Talker → Code2Wav
                    ↓
真实 GPU
```

不重写通用网关、会话调度器或模型算法。第一阶段不引入 PD、量化、投机生成或自定义重叠。必要的兼容补丁独立记录，不能悄悄并入“原版”。服务仅监听本机地址。模型、环境、原始媒体与机器信息不进公开仓库。

## 0. 兼容与资源预检

1. 读取驱动、GPU、空闲显存、磁盘、Python、CUDA、现有包；检查选中 GPU 是否有其他进程。
2. 固定模型 revision、Omni commit/tag、匹配的 vLLM/Torch/CUDA 组合；文档版本与实际源码一致。
3. 创建独立用户目录与环境，保留环境解析、安装日志和来源哈希；不改全局驱动、CUDA 或旧环境。
4. 从导入、GPU 张量运算、attention 小例子到模型加载逐级预检；记录失败原因，不把导入成功算部署成功。

**当前状态**：固定软件版本、模型下载/源哈希校验及两卡运行已完成。驱动为 560.35.03，采用两张 24 GiB RTX 3090。每次新测量仍需复查资源和环境；当前 eager 短回放配置不能直接当作最优性能基线。

## 1. 部署官方双工基线并接入实验程序

优先核验官方两卡部署：Thinker 单独一组，Talker + Code2Wav 另一组。若容量不足，使用官方三阶段布局或有证据支持的并行配置；所有资源变化写入配置。阶段分卡不等于语言模型 PD 分离。

交付：

- 固定版本、安装锁定、启动/停止入口；启动前资源检查，退出后确认释放 GPU。
- 使用官方双工客户端/协议；实验程序只添加输入回放、时间戳与结果归档。
- 输入事件记录 `session_id, event_id, source_start_ms, source_end_ms, ready_ms, media_refs`；媒体必须按可用时间提交，不能提前泄露未来帧。
- 记录发送计划、实际发送、服务确认、首文字、首音频、各输出块、结束、错误、音频时长；关联输入单元与输出，不能把每次调用当作一次完整回答。
- 记录实际引擎类、调度器、attention 后端、缓存统计；不能仅凭 HTTP 地址或安装了 vLLM 判断执行路径。

验收：

1. 文字、音频、视频+音频三类 smoke 均通过。
2. 无问题时持续输入也进入模型计算；后续输入延续同一会话历史。
3. 倾听/说话、跨秒长回答、打断/恢复、输入结束后的输出排空均有日志证据。
4. 返回的声音可解码、有限且非空；抽听及转写/问答检查通过，不以“只研究性能”为由忽略功能。
5. 短会话预热后重复三次；会话重置不串状态；CPU/GPU 时间口径明确。

通过后冻结 B0：官方双工基线。现有静态快照工具不能冒充增量双工测试。

## 2. 充分的压力与瓶颈定位

顺序：单会话 → 单因素变化 → 并发扫描。每个条件先做短预检，再正式重复 3 次；预热、测量、输入结束和排空区间分开。

| 实验 | 控制变化 | 要回答的问题 |
|---|---|---|
| 单会话正常回放 | 真实 1× 时间到达，连续音视频 | 能否长期跟上？哪些片段积压？ |
| 历史长度 | 自然增长并记录真实有效 token/KV；窗口策略固定 | 变慢来自历史还是输入/输出工作量？ |
| 输入密度 | 在模型允许范围改变帧数/分辨率；音频不随意变速 | 输入编码与 P 是否成为瓶颈？ |
| 说话占比 | 多段真实语音/视频，覆盖倾听、短答、长答、打断 | D、语音 token、W 各占多少？ |
| 突发与过载 | 到达节奏固定预生成；允许单会话输入积压 | 排队、丢弃、拒绝或超时发生在哪里？ |
| 多会话 | 开环 N=1,2,4，再按容量细扫 | 增加会话后是否饱和？限制是否只是接纳上限？ |

负载至少覆盖多个来源、多个会话内容；同一视频重复不能算独立样本。先使用合法的官方媒体，再补充公开许可的连续音视频；保存来源与许可。人工文字注入与真实语音输入分开报告。

必须记录：

- 实际到达率、接纳/完成率、拒绝/超时、队列长度与增长斜率、输入新鲜度。
- 首文字/首音频延迟的明确起点；输入确认延迟、音频块间隔及音频生成速率；若无物理播放器，不宣称真实播放无断音。
- P、D/控制、语音 token、W、数据准备和传输的区间；宿主区间不能直接当 GPU kernel 时间。
- 实际输入 token、生成 token、KV 字节、窗口裁剪、缓存重算、GPU 显存、利用率、其他进程。
- 可用时采集引擎队列指标；trace 单独运行，测量插桩开销。

**“压力到了”判据**：稳定工作区与过载区均有测量；过载区出现持续积压、期限违约/拒绝增加，或完成吞吐不再随负载提升。打满客户端/接纳限制不等于 GPU 饱和。报告观测到的服务包络，不草率声称最大容量。

保留全部正式重复，不挑最快；输出原始 JSONL、配置、环境、统计脚本、汇总表和瓶颈图。公开只放可复核的紧凑汇总与生成代码。

## 3. 普通 PD 对照 → 分批 KV 传输

前置门槛：阶段 1/2 通过；证明候选等待确实存在，并测出 KV 规模及目标 GPU 间真实传输成本。现有 Omni 三阶段不是 MiniCPM-o 双工 PD 的现成验证；必须先核验状态接口。

1. 建立 B1：普通严格依赖 PD。P/D 权重与位置配置一致，正确交接本会话 KV；保留倾听/说话、隐藏向量到 Talker 的接口。
2. 在固定前缀上检查 logits、KV 长度/位置及缓存内容；继续完整双工会话，检查控制和输出质量。D 生成历史的返回/延续协议先固定。
3. 保持资源、输入、语义、通信后端、语音/W 放置一致，只改变 P→D 传输提交策略：

| 策略 | 提交时机 |
|---|---|
| B1 整批 | 本秒/本输入单元的 P 完成后 |
| S1 按层 | 本次计算某层新 KV 就绪后 |
| S2 按计算步 | 本轮全部层结束后 |
| S3 阈值 | 按层/步累计，达到字节数或等待期限后 |

“一秒单元”“模型计算步”“单个 token”不是同一粒度；实际重合的策略不重复计数。每份数据带会话、历史版本、层、token 范围和源/目标位置；CUDA 就绪、接收安装完成、引用存活分别处理。未就绪的 KV 不允许 D 使用。

4. 先做真实 KV 的传输微基准（消息大小、数量、带宽、打包/同步、争用），再运行相同双工回放。
5. 测量 KV 就绪到 D 可读的延迟、未隐藏通信、计算重叠、D 启动等待、首音频/尾延迟、额外显存和消息数。
6. 消融：关闭重叠、固定粒度、只在需要回答时同步 vs 持续提前同步；报告无收益和负收益条件。

同一 PD 资源预算比较 S1/S2/S3；B0 与 B1 若 GPU 数不同，另报告资源成本，不能把增卡收益算成策略贡献。W 保持一致，暂不同时发明新 W 策略。

**停止/收敛**：普通 PD 不能正确延续状态就先修正确性；没有可隐藏通信窗口就报告适用边界；新增副本/通信成本超过收益则保留负结果，不强行推进更复杂策略。新增历史交错、丢弃依赖或改模型训练另立任务，不混入本次实验。
