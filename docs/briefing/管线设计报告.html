面向 StreamVLM GPU 架构研究的实验管线设计报告

版本：2026-11-12。面向组内技术汇报。代码仓库：https://github.com/sxq999/stream-VLM 。本报告依据本地实现、仓库验证摘要及 Qwen 官方资料编写；不将规划功能写成已完成结果。

1. 项目定位与本轮交付

本项目希望为后续 StreamVLM 的 GPU 架构研究搭建一套可复用的实验管线。它把“什么时候看到哪些视频帧、什么时候提出问题、调用哪个推理实现、如何测量并保存结果”写成可执行的实验。后续修改 vLLM 调度、KV 内存管理或 CUDA/Triton 算子时，可以通过同一套输入与测量方法比较修改前后的行为。

本轮交付的是 Python 实验控制程序，以及配置、输入格式、测量和验证工具。Qwen3-VL 和 vLLM 是被调用的已有软件。下载权重、部署已有模型、运行 GPU 推理，是验证这套管线能工作的必要步骤；本轮没有训练新模型，也没有提出新的 GPU 优化算法或获得可报告的加速比。

一句话向师兄介绍：我们围绕 Qwen3-VL 搭建了一个受时间约束的流式输入测试平台，能够控制真实 GPU 实验、保存运行证据，并为后续替换引擎或算子提供统一入口。

本轮已经验证与尚未验证的边界

2. 为什么 StreamVLM 需要专门的实验管线

普通离线 VLM 可以一次拿到完整视频后回答问题。流式场景中，视频持续到达，问题可能在任意时刻出现，系统此时只能使用已经到达、满足截止时间的证据。到达节奏、历史长度和并发会话会改变视觉编码量、prefill 长度、KV 使用和请求等待。

因此，直接写一次 model.generate() 只能证明模型能推理，难以回答以下体系结构问题：某个改进是否在持续输入和并发下仍有效？首段回答变慢来自输入等待、客户端队列，还是引擎内部？是否通过少看帧、缩短输出或改变缓存状态取得了表面加速？能否找到当次运行使用的代码和参数？

管线的作用是固定实验条件，并保留足够证据。它自身也会产生开销，所以测量必须分清客户端行为、引擎行为和 GPU 行为。

3. 当前基座模型：Qwen3-VL-8B-Instruct

3.1 模型架构与实际计算流程

当前验收对象是 Qwen3-VL-8B-Instruct 的 dense 版本。不能把其他 Qwen 分支的 GDN、QSA、MoE 结构直接套到这个检查点。官方模型配置给出的主要结构如下。[S1][S2]

部分 本检查点配置 对 GPU 研究的意义
视觉编码器 27 层，hidden size 1152，16 heads 图像处理规模影响视觉计算与中间特征
图像 patch 与合并 patch size 16，spatial merge size 2，temporal patch size 2 预处理后的网格影响视觉 token 数，不能只记录原视频分辨率
视觉到语言接口 输出维度 4096，DeepStack 索引 8/16/24 多层视觉特征参与语言网络计算，需要核对特征生命周期
文本解码器 36 层，hidden size 4096，MLP intermediate 12288 注意力、MLP 和归一化等形成主要算子路径
Attention 32 query heads，8 KV heads，head dimension 128 使用 GQA，KV 存储按 KV heads 计算
位置编码 interleaved MRoPE 位置构造须与模型的图文/视频输入语义匹配

计算路径可以按以下顺序理解：CPU 读取和预处理帧与文字；把图像张量和 token 交给模型；视觉编码器生成特征；视觉合并与 DeepStack 接口把特征交给语言部分；语言网络对输入上下文执行 prefill；随后逐步 decode，生成回答。

这里的 prefill 指处理当前请求的输入上下文并建立该请求所需的状态。decode 指在已有上下文上继续生成输出。当前本地部署为了工程验收将 max-model-len 设为 4096；这不是模型官方上下文能力的上限。

官方介绍中的三项结构更新是 interleaved MRoPE、DeepStack，以及视频的文本时间戳对齐。[S3] 当前 HTTP 与 native 适配器都逐帧插入自定义 [source PTS ...s] 文本标签，再提交历史图片和当前问题。这让模型收到来源时间文字，但尚不等同于官方原生视频张量、时空网格与时间戳组织的完整输入路径。capture、ready 和 evidence_cutoff 等控制字段仍由管线用于可见性约束。

3.2 一个与 GPU 架构有关的具体估算

对该 dense 文本解码器，若 KV dtype 为 BF16、单份缓存、单 GPU、不考虑对齐与分页冗余，每个上下文 token 的理论 KV 数据量为：

2(K 和 V) × 36 层 × 8 KV heads × 128 head_dim × 2 bytes = 147456 bytes = 144 KiB。

4096 个 token 的理论原始 KV 数据量约为 576 MiB。这只是按配置推导的存储量，不是当前实测显存。真实显存还包括权重、视觉特征、临时张量、缓存分配粒度和运行时开销；KV 量化、并行切分或其他缓存机制也会改变结果。该估算的作用是建立“历史越长、并发越多，为何需要关注 KV”的量级直觉。

4. 软件栈与职责边界

实验配置 + 事件清单 + 帧文件
              ↓
Python 管线：回放时间、维护会话、提交请求、测量、归档
              ↓
后端适配器
      ├─ HTTP：调用本机 vLLM 服务
      └─ Native：直接调用 Transformers 参考实现
              ↓
推理实现：模型执行、批处理、缓存、算子选择
              ↓
PyTorch / 自定义 CUDA / Triton / CUDA 库
              ↓
真实 NVIDIA GPU

这个分层是职责说明，不是一条每次都严格经过所有节点的调用链。vLLM 包含 Python、C++/CUDA 等代码，也可能直接调用自定义算子；PyTorch 是库，不是另一种语言。HTTP 是进程之间的接口，不会让服务端代码变得不可修改。

管线中的 CPU 逻辑负责“什么时候向哪个服务提交哪些请求”。vLLM 内部调度器负责“哪些请求一起执行、如何分配 KV、如何组织模型执行”。CUDA/Triton 算子负责在 GPU 上完成具体计算。改变客户端并发，不等于修改了 vLLM 的 GPU 调度算法。

后续优化 vLLM 时，可以在独立源码目录与环境中安装修改版，再让配置指向修改版环境和源码路径；优化 CUDA/Triton 时，将算子实现集成到被测引擎路径中。管线通过相同输入调用它们，同时记录实际版本。只有更换接口语义或测量需求时，才需要扩展适配器。

5. 管线的总体设计

5.1 六个职责模块

模块 主要代码 输入与输出 设计理由
输入与会话 events.py JSONL、图像 → 经过约束的帧快照 防止未来证据泄漏和会话串扰
回放与提交 runner.py 配置、事件 → 请求及时间线 控制到达节奏、客户端并发和待处理预算
后端适配 backends.py、native.py 帧快照、问题 → 响应或错误 隔离实验控制与推理实现
部署生命周期 deployment.py 引擎启动参数 → 可用服务及日志 让实验自动落到真实 GPU，并结束自有进程
负载与实验套件 workloads.py、suite.py 模板与实验列表 → 一组成组实验 系统改变到达方式和并发，保存失败与预热结果
测量、身份与分析 report.py、identity.py、stages.py 原始记录 → 指标、trace、源码快照 解释性能并追溯到具体实现

这是一套研究实验工具，当前不以摄像头应用界面、生产级服务或硬件模拟器为交付目标。

5.2 两种真实计算后端

HTTP / vLLM 路径用于部署与 serving 实验。管线把图片、source PTS 文本标签和当前问题组成 OpenAI-compatible 请求，发送到本机 http://127.0.0.1:8100/v1/chat/completions，读取 SSE 文本流并保存完成标记、usage 和服务端 request ID（若服务提供）。当前每次构造单条 user message，不自动附上先前问题与助手回答的对话历史。这条路径适合后续观察 vLLM 调度、内存和算子的整体作用。

Native / Transformers 路径直接加载本地权重执行参考推理，并在请求和指定模型模块外设置 profiling 范围，帮助理解视觉与语言计算。当前后端串行保护模型调用，返回完整回答，不提供 native 首 token 时间。两种后端的执行策略不同，不能把其延迟差直接解释成某个算子的加速效果。

mock 后端只用于低成本检查管线逻辑，不运行真实模型，也不能产生 GPU 性能结论。

6. 数据格式：如何把视频变成可控实验

6.1 当前实际输入

当前管线的执行入口是 JSONL 事件清单 + 清单目录内的图像文件。已有验收使用程序生成的红、蓝、绿方块图像，目的在于检查会话、历史和真实推理路径。这些图像不是代表性视频基准，不能用于证明真实 StreamVLM 场景的性能或任务能力。

在真实视频实验中，可以先下载或采集完整视频，再由离线准备步骤抽帧、生成清单。执行阶段仅按清单放行已经到达的帧，模型不会直接拿到完整视频路径。当前 runner 不会自动从任意 MP4 中建立完整的视频解码与音频管线；必须先准备相应帧和清单。

因此当前系统同时包含两件事：输入时间和交互事件由软件回放模拟，模型计算由真实 GPU 执行。它不是 GPU 硬件模拟器。

6.2 事件类型与关键字段

类型 含义 关键字段
frame 一帧或一个图像证据准备就绪 session_id、event_id、source_seq、capture_start_ms、capture_end_ms、frame_pts_ms、ready_ms、image_path
query 用户在某时刻提出问题 ready_ms、evidence_cutoff_ms、prompt
cancel 请求取消某一已有问题 query_id、session_id
close 结束会话并清理该会话输入 session_id、ready_ms

所有事件具有 schema_version、session_id、全局唯一 event_id 和 ready_ms，并按 ready_ms 排序。source_seq 在同一会话内从零连续增长。图片路径必须落在清单目录内且文件存在。

{"schema_version":1,"kind":"frame","session_id":"a","event_id":"af0","source_seq":0,"capture_start_ms":0,"capture_end_ms":1000,"frame_pts_ms":500,"ready_ms":1000,"image_path":"red.png"}
{"schema_version":1,"kind":"query","session_id":"a","event_id":"aq0","ready_ms":1000,"evidence_cutoff_ms":1000,"prompt":"What color is the square? Answer with one color word."}

时间字段有两类：capture/PTS 表达来源视频的时间，ready 表达在本次回放中的可用时间。复制会话、错开到达时，不应把来源视频时间一起改掉。

6.3 帧可见性与不可变快照

查询只能取同一会话中已经保留、capture_end_ms ≤ evidence_cutoff_ms 且 frame.ready_ms ≤ query.ready_ms 的帧。清单检查还要求帧采集结束不晚于其就绪时间，查询截止时间不晚于查询就绪时间。

runner 在接纳查询时生成固定帧快照。随后新到达的帧不会补进已提交查询。这样即使请求在客户端队列中等待，也不会因为“执行时已经更晚”而看到未来帧。

这一约束证明的是清单协议内的因果可见性。真实视频到清单的制作还需检查抽帧、时间戳和内容来源，避免输入准备阶段就引用未来信息。

6.4 具体回放例子

  1. 1.000 秒，A 会话红色图像、B 会话蓝色图像就绪。
  2. 同一时刻分别提交“是什么颜色”。A 查询只拿到 A 红图，B 查询只拿到 B 蓝图。
  3. 2.040 秒，A 新的绿色图像就绪，再问“第一个方块是什么颜色”。使用 full 策略时，此请求快照含 A 红、绿两图；旧查询快照保持不变。

这里的“记住第一帧”来自重新提交保留的历史图像，不能据此宣称服务端维护了跨查询的视觉记忆或持续 KV。

6.5 语音与交互的当前边界

当前 query.prompt 是预先写入的文字输入，ready_ms 控制其出现时间。它可以表达“某时刻用户问一句话”这个事件，但没有实现麦克风、ASR、音频 token、TTS 或原生双工状态机。cancel/close 可测试控制流程；客户端发出取消不等于已经证明服务端即时回收对应 GPU/KV 资源。

7. 调度、历史与实验配置

7.1 回放方式

realtime 按清单就绪时刻相对本次实验起点放行，适合端到端时延。fastest 按事件顺序尽快处理，适合功能检查和快速回归；不再用名义就绪时间计算实时延迟，相关字段设为 null。

7.2 两个客户端预算

concurrency 控制 Python 请求工作线程数。pending_capacity 限制已接纳但尚未释放的请求总量，包括排队与执行中的请求。预算满时显式失败，避免无限积压或静默丢弃。vLLM 的 max-num-seqs 等参数属于服务端独立控制项，不能与客户端 concurrency 混称为 GPU 并行度。

7.3 历史保留

full 策略保留所有帧至 max_frames，超限显式报错。recent 策略只留最近 max_frames，并记录丢弃帧 ID。二者输入语义不同；比较性能时必须标明是否减少了历史，否则不能把少计算等同于实现优化。

7.4 配置与负载变化

配置可以改变后端、模型、GPU、帧预算、回放模式、并发、启动参数与源码路径。workload 命令可复制模板会话并错开到达时间，当前支持最多 64 个复制会话；复制形成负载变化，不产生独立的语义样本。suite 管理命名 case、预热与重复次数。每个 managed case 拥有自己的服务生命周期，同一 case 中多个重复共享服务，可能共享其缓存状态；当前不会在每轮之间隐式清空缓存。

8. 一轮真实 GPU 实验如何执行

  1. 读取配置与清单，确定模型目录、引擎 Python 环境、GPU 和输出目录。
  2. managed 部署检查 GPU 空闲显存和端点占用情况，启动自己的 Linux 进程组。
  3. 轮询 /v1/models，等待模型服务就绪。模型加载进 GPU 由所启动的 vLLM 完成。
  4. 建立实验时间原点，回放帧和查询，后端提交请求并读取输出。
  5. 保存时间线、结果、指标、资源采样与版本身份；profile 模式另存 GPU trace。
  6. 正常或异常结束后，终止并回收自己启动的进程组。不会停止原本已存在的他人服务。

模型部署启动时间在 managed deployment 中单独保留；回放指标的时钟在 run 内启动。因此当前首段响应指标不包含冷启动加载时间。若研究冷启动，需要从 deployment 记录另外建立测量口径。

当前 configure_local.py 生成的真机验收配置使用 BF16、单个指定 GPU、max-model-len=4096、max-num-seqs=4、每请求最多两张图片、gpu-memory-utilization=0.90 和 enforce-eager，并设置图像预处理预算。这个配置是小规模验收基线，不是针对所有视频工作负载调优过的最优部署。通用 configs/qwen3vl.json 的图片上限与此生成配置不同，汇报和复现实验应以当次归档 config 为准。

9. 测量：能回答什么，不能回答什么

9.1 客户端时钟上的指标

令 r 为查询名义就绪时刻，a 为接纳时刻，s 为请求线程开始时刻，f 为首段非空文本时刻，d 为请求完成时刻。当前 realtime 指标为：

指标 定义 含义和边界
接纳延迟 a − r 客户端回放/处理跟不上名义到达的程度
客户端队列 s − a 在线程池中等待，不是 vLLM 内部队列
首段文本延迟 f − r 包含客户端影响与引擎处理，不能精确等同 GPU 首 token 时间
完成延迟 d − r 当前查询从名义到达到完成的总时间
文本块间隔 相邻 SSE 文本块时间差 SSE chunk 不保证一 token，不能称为 TPOT
观测吞吐 完成查询数 / 回放观测时间 包含输入节奏，不能称最大或饱和吞吐

报告生成 p50/p95，并保留逐查询原始值。少量验收请求的分位数不构成稳定性能结论。失败、取消和未完成状态需要与延迟一起看，不能只挑最快成功样本。

9.2 GPU 与引擎观察

resources.jsonl 通过 nvidia-smi 约每两秒记录显存、利用率和功耗。这是 GPU 设备级采样，会受到其他进程影响，也可能漏掉短暂峰值，不能作为请求级 kernel 时间或精确能耗。

native trace 使用 PyTorch profiler，并通过模块 hook 标出视觉编码器、首次语言 forward（prefill）及后续 forward（decode）。这些标签适用于当前 native generate 路径，CPU range 时长不能直接当作 GPU 独占时间。

vLLM profile 通过真实引擎的 /start_profile 与 /stop_profile 收集服务端 trace。已确认其中包含 CUDA kernel 与 memcpy。当前 trace 没有自动建立每个请求到每个 kernel 的完整归属，因此不能凭请求在客户端重叠就宣称 GPU kernel 并行，也不能从未标注的引擎 trace 推导逐请求各阶段占比。

profiler 会改变执行和时延。诊断运行用于找执行路径；性能比较应使用配对的非 profiling 运行。本文不报告任何加速比。

10. 版本、归档与可复现性

每轮输出写入新的目录，已有目录不被覆盖。典型 managed 输出包括：

run/
  deployment/               启动参数、引擎环境、启动日志与生命周期记录
  measurement/
    config.json              本次最终配置
    environment.json         输入/代码/环境身份
    timeline.jsonl           原始事件时间线
    summary.json             每个查询的结果和状态
    metrics.json             逐查询指标及汇总
    resources.jsonl          设备采样
    source_snapshot/         本次管线 Python 源码
    implementation_snapshot/ 配置后可保存外部源码差异等
  traces/                    profile 模式的独立诊断产物

记录内容包括输入清单与图片哈希、管线源码哈希和拷贝、包版本、GPU 清单、模型 SOURCE_LOCK 身份。若指定外部引擎源码 components，还记录 Git commit、tracked diff 和 untracked 文件身份/有限快照。若只安装 wheel，包版本不能证明外部修改源码的身份。快照有体积预算，不应误解为任意大工程的完整备份。

锁定身份让结果可追溯，但不自动消除硬件争用、系统状态和数值非确定性。严谨的候选比较仍需固定资源和实验协议。

例如修改一个视觉算子：基线环境装原版 vLLM，候选环境装修改版。二者都运行同一份事件清单、相同预处理和输出限制。先核对实际加载了候选算子，再做数值检查及独立 profiling；最后用匹配的非 profiling 运行比较时延和失败。不能通过切换 recent 丢掉帧，或在候选中缩短回答来冒充算子收益。

即便研究不以回答质量为主，仍需做基本计算正确性检查。CUDA 改动若产生错误数值，速度再快也不能支持有效架构结论。若未来算法主动改变计算量，则需另行规定任务质量或可接受误差约束。

13. 管线如何“收敛”

管线的收敛依据是事先写明的能力合同和验收，而不是不断加入模型或不断追逐更低延迟。针对当前 Qwen3-VL 单机实验底座，可以用以下闭环判断是否够用：

  1. 同一输入事件能生成可解释的帧快照，未来帧与其他会话帧不会混入。
  2. 管线能在指定环境/GPU 上启动真实模型并完成工作负载，异常也能留下记录并清理自有服务。
  3. 性能指标有明确时间点、单位与限制，GPU 诊断确实发生在引擎端。
  4. 每个结果能追溯到输入、配置、模型和实际实现，能够按运行手册复现。
  5. 更换一个保持接口兼容的候选引擎，不需要改写事件与测量主逻辑。

当前已用小规模合成输入验证核心闭环。要把它称为“代表性 StreamVLM benchmark”，仍需另行确定真实数据、时长、会话数、交互模式和统计协议。要宣称支持持续 KV、语音或 PD，也必须分别补实现与专项验收。边界明确后，框架即可冻结，后续围绕具体研究问题增加必要观测，而不无限扩展平台。

14. 师兄可能追问的回答

为什么选 Qwen3-VL？ 当前它是已经实际部署并验证的基座，能连接视觉编码、语言 prefill/decode 和成熟 serving 实现，适合作为第一条可检查的计算路径。我们没有证明它优于其他基座；模型选择可以随研究问题调整。

到底做的是 StreamVLM 算法还是管线？ 本轮做管线，以 StreamVLM 的持续输入与交互约束组织实验。算法和 GPU 优化是后续使用管线开展的工作。

整段视频已在硬盘，怎么保证不偷看？ 执行端只按清单接纳到达的图片。查询接纳时固定帧快照，同时按来源截止时间过滤。视频到清单的制作也要审核时间戳。

有 KV cache 吗？ vLLM 在单次生成中使用自己的 KV 机制；当前适配器不能保证跨查询复用同一连续会话 KV。重新发送历史前缀不等于持续增量状态，是否有引擎缓存命中需另测。

能不能直接改 GPU？ 软件能调用真实 GPU，也能比较软件对 GPU 的使用方式。若研究改变 GPU 微架构本身，还需要合适的硬件模拟器、RTL/原型或可验证的建模链路，当前管线不会自动完成这部分。

现在得到什么研究结论？ 现在得到的是工程通路已运行的证据，尚未得到瓶颈占比、加速机制或可发表的性能结论。下一阶段应先选择代表性 workload，再由 trace 提出可被证伪的瓶颈假设。

15. 操作入口与参考来源

常用入口及完整参数以仓库 RUNBOOK.md 和 CLI 为准。以下为 Linux 示例，环境和权重路径需指向实际机器，输出目录每次使用新名字。

# 生成指向本地权重与引擎环境的配置
python scripts/configure_local.py --model-dir /path/to/Qwen3-VL-8B-Instruct \
  --engine-python /path/to/engine-env/bin/python --gpu 0 --out runs/base-config.json

# 自动启动服务、执行、归档、结束服务
python -m stream_pipeline experiment --config runs/base-config.json --out runs/base-001

# 独立的引擎诊断运行
python -m stream_pipeline profile --config runs/base-config.json --out runs/profile-001

# 基于模板构造四会话到达负载
python -m stream_pipeline workload --manifest examples/visual/events.jsonl \
  --sessions 4 --stagger-ms 250 --out runs/workload-four

工作负载生成后，需要将新配置 manifest 指向生成的清单；以上 workload 命令本身不会启动推理。原始配置的帧上限、引擎图片上限和上下文长度要与新输入一致。
