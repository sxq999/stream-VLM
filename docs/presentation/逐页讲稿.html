StreamVLM 管线设计汇报讲稿

对应八页汇报。主讲约十至十二分钟，可按讨论需要展开。每页均以连接上一页的口语开场，随后沿图说明动作和接口。

01_管线总图

师兄好，这次汇报只介绍管线设计。先看这张总图：左边是我们准备好的帧文件和事件清单，右边是实际运行模型的 vLLM 与 GPU，中间蓝色区域是我们的管线。输入进入后，先按时间放行，再进入对应视频的历史列表。有问题到达时，管线选好帧，组成请求，交给 vLLM。vLLM 算完以后，管线接回回答，把这次输入和执行时间一起记下来。上方的实验控制器负责启动和结束这整个过程。下面先说明一组实验怎样跑起来，再展开中间的运行流程。

来源：本项目 events.py、runner.py、backends.py、deployment.py、suite.py、identity.py、report.py。 https://github.com/sxq999/stream-VLM/tree/34b4218/src/stream_pipeline

02_一组实验如何运行

上一页介绍了系统由哪些部分组成。这一页看一组实验怎样运行。上面一行是我们的管线，下面一行是 vLLM 和 GPU；从左到右是准备、运行和收尾。首先，控制程序启动 vLLM，模型加载由 vLLM 完成，管线会等它准备好。就绪以后，才进入中间的运行阶段：管线发送输入，引擎计算，再把响应返回。我们可以在同一个服务上预热并重复回放。最后，管线保存记录，关闭自己启动的服务。接下来的四页，都是展开中间这段运行阶段，不是另外一套流程。

来源：本项目 events.py、runner.py、backends.py、deployment.py、suite.py、identity.py、report.py。 https://github.com/sxq999/stream-VLM/tree/34b4218/src/stream_pipeline

03_输入如何按时进入

现在进入运行阶段的第一步：按时间放行输入。图片文件回答看什么，事件清单回答什么时候看、什么时候问。这里用同一个例子贯穿后面的图：一路视频叫 A，帧依次叫 A0、A1、A2。清单规定它们在一秒、两秒、三秒到达，三点五秒提出问题 Q0，四秒再到达 A3。程序从回放起点开始计时，到点就把对应的帧或问题交给下一步。即使 A3 已经在硬盘里，也要等到四秒才放行。问题放行后，下一步才决定它可以使用哪些历史帧。

来源：本项目 events.py、runner.py、backends.py、deployment.py、suite.py、identity.py、report.py。 https://github.com/sxq999/stream-VLM/tree/34b4218/src/stream_pipeline

04_查询如何选择历史帧

第二步是维护历史并为问题选帧。这里明确选用只保留最近两帧的配置，方便说明窗口怎样工作。A2 到达前，列表里是 A0 和 A1；A2 到达后，A0 被淘汰，留下 A1 和 A2。到了三点五秒，Q0 只从视频 A 的这个列表里选帧，并检查截止时间。选中的 A1、A2 会固定下来，后面排队多久都不再变化。四秒到达的 A3 只影响新问题。这里管理的是 CPU 历史列表，不是在删除 GPU 的 KV；下一步会把选好的两张图重新组成一次请求。

来源：本项目 events.py、runner.py、backends.py、deployment.py、suite.py、identity.py、report.py。 https://github.com/sxq999/stream-VLM/tree/34b4218/src/stream_pipeline

05_一条请求如何执行

帧选好以后，Q0 就成为一个明确的请求：两张图片，加上一句问题。管线先检查还能不能接下这个请求，然后进入等待队列，由 CPU 上的 Python 工作线程发起调用。这里的线程不是 CUDA 线程。工作线程把图片、来源时间文字和问题通过本机 HTTP 接口发给 vLLM；vLLM 再决定怎么组 batch、怎么使用 GPU。HTTP 是两个程序之间的调用接口，不需要访问外部网站。回答返回以后，适配器把文字和完成状态整理成记录，交给下一页的结果模块。一次调用并不对应一个 GPU thread，也不保证对应一个固定大小的 batch。

来源：本项目 events.py、runner.py、backends.py、deployment.py、suite.py、identity.py、report.py。 https://github.com/sxq999/stream-VLM/tree/34b4218/src/stream_pipeline

06_结果如何记录

运行阶段的最后一步是记录结果。我们用同一个请求编号 Q0，把使用的帧、回答和状态串起来；问题文字可以通过输入清单查到。上面的时间线标出几个实际记录的动作：问题就绪、管线接纳、线程开始调用、收到首段文字、回答完成。相减就能得到客户端排队、首段响应和完成延迟。下面的目录保存原始记录、指标，以及这次实际使用的配置和代码身份。这样之后看一条结果，能够找到它对应的输入和实现。这里测的是客户端看到的全过程，若要分析 GPU 内部计算，还需要另外跑引擎 trace。到这里，一次回放的主要流程就讲完了。

来源：本项目 events.py、runner.py、backends.py、deployment.py、suite.py、identity.py、report.py。 https://github.com/sxq999/stream-VLM/tree/34b4218/src/stream_pipeline

07_如何安排多组实验

前面讲的是一组配置怎样运行。接下来把这套流程重复起来，就能做多组实验。图中举两组：输入、模型和 GPU 都相同，只把 CPU 请求并发上限从一改成四。每组仍然先启动并等服务就绪，然后预热、正式重复，最后停止服务。注意层次：一组配置启动一次服务；服务运行期间可以回放多轮；每轮回放里面又有多个问题。各轮结果分别保存，便于比较。这里的批量运行指重复做实验，不是 GPU 的 batch。同组没有自动逐轮清空引擎缓存，这个条件也要随配置一起说明。

来源：本项目 events.py、runner.py、backends.py、deployment.py、suite.py、identity.py、report.py。 https://github.com/sxq999/stream-VLM/tree/34b4218/src/stream_pipeline

08_Q0 的完整路径

最后回到总图，用 Q0 走一遍。服务已经准备好，三点五秒时，门控放行这个问题。视频 A 的历史窗口此时是 A1、A2，所以管线固定这两帧，把它们和问题文字交给请求模块。通过接纳检查后，CPU 工作线程调用 vLLM，引擎完成 GPU 推理并把响应返回。结果模块再以 Q0 为关联键，保存帧来源、回答状态和时间。四秒到达的 A3 不会补进这个请求。这样从输入到输出，每一步由谁负责、传递什么、保存什么，都能在同一条路径上对应起来。

来源：本项目 events.py、runner.py、backends.py、deployment.py、suite.py、identity.py、report.py。 https://github.com/sxq999/stream-VLM/tree/34b4218/src/stream_pipeline
